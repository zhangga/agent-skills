# 个人 Agent 知识交接

日报、历史补记和周报保存后都自动导出完整资料。`memory.py export --config <config> --run-id <已保存运行ID>` 可补导出或修复输出；不采集、不发送、不推进采集基线。query 仅查询，不自动建立一份新资料。

## 文件与读取入口

输出到 `config.agent_export_dir`，默认 `<archive_dir>/agent`。`<mode>` 为 daily、bootstrap 或 weekly：

| 文件 | 用途 |
| --- | --- |
| `<mode>/<run-id>.zip` | 可携带的完整资料包：source.md、source.json、items.jsonl、HANDOFF.md、manifest.json |
| `<mode>/<run-id>.md` / `.json` | 自包含的总结、事项正文、历史、来源、验证证据及覆盖缺口 |
| `<mode>/<run-id>.items.jsonl` | 每行一个完整事项及其来源证据，适合分批提炼 |
| `<mode>/<run-id>.handoff.md` | 本次资料标识、范围、预期数量、提炼原则和收录回执格式 |
| `latest.md` / `.json` | 截止时间最新的一份完整资料副本，不是另一条来源 |
| `latest-daily` / `latest-bootstrap` / `latest-weekly` 的 `.md` / `.json` | 对应模式最新的一份完整副本；旧周报入口兼容保留 |
| `manifest.json` / `index.md` | 已导出资料清单，供机器同步和人工查阅 |

旧清单中没有 mode 的条目按 weekly 解释。未运行过的模式没有 latest 入口。固定入口按窗口结束时间排序，补导出旧历史不会倒退。

档案内 `<mode>/<run-id>.agent-evidence.json` 冻结导出依据。同 ID 重试保持冻结内容，可修复丢失的派生文件。旧运行首次补导出时注明是从现存档案补建，不能冒称原总结生成时就已冻结。事实修订要保存新版本，不能借 export 改写旧来源。

## 内容与知识提炼

每份导出包含**统计窗口内全部已保存的记录**，可能与上一份日报或周报重叠，不仅是本次新增记录。窗口是 `[since,until)`；窗口外的后续进展不能覆盖窗口内状态。各项目/事项保留最新记录和历史，以及背景、步骤、技术取舍、验证条件、产物、限制、可复用知识、后续动作与原始来源。缺失字段不自动补造。完整资料是已提炼的工作档案，不是全部原始对话和工具日志。

`items.jsonl` 的字段：

- `unit_id`：由 project_id + item_id 确定的稳定事项标识；`content_sha256` 为该事项材料摘要。
- `document_id` / `document_sha256` / `window`：所属资料版本与时间范围。
- `latest` / `history`：完整进展，含 revision_id、source_run_id、record；不裁切长文本。
- `revision_hashes`：revision_id 到记录内容摘要的映射，跨日报/周报去重，也能发现后续详情修订。
- `source_catalog` / `evidence_catalog`：该事项引用的来源及实际已保存的证据；保留 missing_event_ids / missing_evidence_ids。
- `extraction_status=candidate`：待提炼材料；脚本没有把它自动提升为已验证知识。

让接收方按 [交接说明模板](../assets/agent-handoff.md) 提炼：项目事实与约束、排障方法、决策及理由、失败经验和适用边界。每条知识附项目、环境、证据日期、验证范围、来源进展和事件。优先读 knowledge 和 details，再核对历史修正；普通进度留在工作记录，未完成行动留作待办，不强行生成知识。

## 实际交付

完成本地导出后，向用户提供本次 `.handoff.md` 和完整正文/资料包的真实路径。不要只给 latest 或卡片标题，让接收方猜是哪一版资料。

- **同机、接收方可读目录**：交给接收方本次 `.handoff.md` 和 `.json`/`.items.jsonl`；长期同步扫描 manifest，按 document_id + content_sha256 去重。
- **通过飞书等聊天交接**：用户授权交付完整资料时，使用该服务支持的文件或文档入口，优先发送接收方能读取的完整 `.md` 加交接说明；支持压缩包再发 `.zip`。若有 lark-im / lark-drive 能力，按其文件上传/发送流程办理。原有“只发送简报”授权不能扩成自动发送全部档案。
- **接收方有知识库入口**：在用户指定空间内走其受支持的导入接口，记录返回的来源 ID。没有可用写入入口时保留导出并报告缺口，不直接编辑助理的数据库、Raw 或知识目录。

发送前确认接收方支持文件类型及大小。若单文件过大，按 items.jsonl 的完整事项分批，随附文档 ID、分片序号、总片数和校验值；不能直接截断正文。文件发送成功后核对附件/文档可读取的实际正文或下载校验，回读标题不够。不能把本机路径、127.0.0.1 或 codex:// 地址当成另一台机器可访问的正文。

飞书卡片适合用户速读，引用卡片的消息读取接口可能只返回标题或客户端升级占位文字；即使完整读取卡片，它仍然只有精选摘要。因此个人助理收录必须交付正文。用户只要求发卡片时仍只发卡片，说明完整资料已在本地准备，不宣称已入库。

## 去重、基线与验收

文档按 document_id + content_sha256 去重；跨窗口按 project_id + item_id 归并，按 revision_id + revision_hashes 去重进展。较窄窗口不包含旧进展不表示删除。发生日期、生成时刻和冻结时刻各自保留；同一事项在不同条件下的结论与后续撤回不能无声合并。

生成完成、文件发送成功、来源入库、知识提炼是四个独立阶段。脚本只返回 `export_status=prepared`，其余收录/提炼状态为 unverified。如用户要求完成入库，取得接收方实际回执：文档 ID 与哈希、保存/重复/失败数量、来源 ID、知识页 ID 或链接，以及回读验证结果。回执格式见交接说明模板。仅保存了“请记录”请求、会话执行结束或收到“任务已完成”卡片都不证明正文入库。

接收方收录游标只在保存与回读成功后推进；保留失败分片。Codex 会话采集仍使用原档案的 state.json，不能以导出截止时间或对端入库时间覆盖它。导出失败时，先检查 runs 中是否已提交；已提交就用同 run-id export 修复，不重采、重置状态或换 ID 重复消费事件。
